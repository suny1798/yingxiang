2. 维护关闭新写和新生成，等待现有有界上传结束；停旧FastAPI和后台保存循环，阻断8788直接写旁路及Webhook。确认没有可继续写源库／媒体的进程。unknown及风险预留不返还。
3. 在`backend/`执行联合快照：`python -m scripts.joint_snapshot snapshot --source data --destination backups/<批次>/joint --offline`；随后`verify`与`restore`到全新`backups/<批次>/frozen-source`。快照目标不能位于源data内。
4. 使用迁移凭据显式Flyway到V3；配置`YINGXIANG_IMPORT_DSN`环境变量（不把DSN写进参数或报告），指定全新`data/java-live-<批次>`私有卷。
5. 创建正式计划：`python -m ops formal-plan --source backups/<批次>/frozen-source --snapshot backups/<批次>/joint --storage data/java-live-<批次> --batch <批次> --output backups/<批次>/formal.plan.json --offline`。此操作只核验快照并读取目标身份；计划2小时有效，不自动停进程、不自动切流。
6. `python -m ops import --source ... --schema yingxiang_migration --storage ... --batch ... --formal-plan backups/<批次>/formal.plan.json`，再分别`verify`、`seal`。源／目标／卷／批次不符、非空冲突、计划过期、并发操作或任何差异都停止；正式导入禁止`--rehearsal`及故障注入。不能手工伪造sealed状态。
7. Java以**维护模式**启动，Worker关闭，端口8792，使用独立运行账号。**Java的storage-root必须指向导入卷的users子目录**，如`data/java-live-<批次>/users`；导入／备份工具则接收卷根。检查ready、原有效会话、私有媒体Range、角色、匿名、未知API和503；此时仍可直接回退。

## 备份与恢复

正式运行后的共同恢复点必须覆盖PG与私有卷：先维护停写／停Worker，再`python -m ops.pg_backup snapshot --backup <全新受保护目录> --storage <Java卷根> --offline`。官方PG18的`pg_dump`需在PATH（或由经过验证的备份执行器调用），凭据只由`YINGXIANG_IMPORT_DSN`转换为工具环境变量，命令行不带密码。`verify`只核验备份；`restore`只接受没有正式schema的新数据库和不存在的私有卷，禁止覆盖活动数据库或原卷。恢复为新账号重新授予权限，不能把`--no-acl`恢复误当成账号权限已恢复。

PG已接收新写入后只允许保持新主库向前修复，或按该共同恢复点恢复PG/媒体并保守核对外部副作用；没有PG反向导出SQLite能力。云备份/PITR、保留策略、容量和RPO/RTO须按实际资源验证，本轮不承诺数值。
